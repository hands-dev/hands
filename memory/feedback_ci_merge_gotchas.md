Three pitfalls hit repeatedly on 2026-06-11:

1. **commitlint enforces lower-case subjects** — the *entire* subject must be lowercase. Write `(eng-962)` not `(ENG-962)`, and keep ALL uppercase out of the subject: SCREAMING_CASE (`E_TASK_NOT_FOUND`), acronyms (`ATS`), and camelCase identifiers (`execFileSync`, `NSAllowsArbitraryLoads`) all fail `subject-case`. Reword those into the body (body casing is unrestricted). Confirmed again 2026-06-24 — `ATS`/`execFileSync` in a subject failed.
2. **The "Validate Linear Cycle Membership" gate requires the referenced ENG ticket to be in the *current* cycle** — referencing an old ticket (e.g. reopening ENG-860 from a past cycle) fails the gate until the ticket is moved to the current cycle. Note: `save_issue` with `cycle: "current"` sometimes doesn't stick — pass the cycle ID explicitly. **Confirmed 2026-06-25: the gate extracts the FIRST `ENG-\d+` match in the PR body and validates only that one.** An *incidental* reference to an old ticket as context (e.g. "…read EXIF/GPS, ENG-984) …" near the top) trips it even when the real work ticket is current and present as "Closes ENG-1059" lower down — it picked ENG-984 (past cycle) and failed. Keep the current-cycle ticket the ONLY `ENG-XXXX` in the PR body — OR at least make it the FIRST match (lead with `Closes ENG-XXXX.`). Write incidental references without the bare number, e.g. "the EXIF GPS read". **2026-07-15 correction:** `gh run rerun [--failed]` REPLAYS the original event payload (the PR body as it was at open), so it does NOT pick up a body edit — the gate re-reads the stale body and fails again. Push a commit (a `synchronize` event) to force the gate to re-read the *current* body. (Hit this exactly: a PR body opening with "reversing ENG-1216…" made the gate pick ENG-1216 (past cycle) over the real ENG-1281; leading with `Closes ENG-1281.` + a push fixed it.)
3. **`gh pr checks --watch` can exit before late-registering checks appear**, reporting green prematurely. Poll instead: loop on `gh pr checks <number>` (use the PR number — branch names can return empty output, which a naive grep counts as zero pending), treat empty output as "keep waiting", and fail fast on any `fail` line.

More hit 2026-07-29 (ENG-1384, adding a new device-authed route + touching the fleet):

4. **A new `app.route('/v1/…')` mount MUST be registered in `SELF_AUTHED_PREFIXES` (`apps/api/src/middleware/route-owns-auth.ts`)** if the router owns its own auth (device bearer / self-auth). `route-owns-auth.test.ts` scans `index.ts` for every `/v1` mount and fails any that's neither in `SELF_AUTHED_PREFIXES` nor the legacy-auth set — and it's a REAL bug, not just a test: the blanket gate 401s the route's device-bearer callers. Add the prefix next to the sibling (e.g. `/v1/chat` beside `/v1/conversations`).

5. **A new `captureException`/`captureWithTags` callsite (or any plaintext-egress/sink) trips the Data Classification Ratchet** — `packages/db/src/security/__tests__/data-classification-register.test.ts` snapshots a per-file "sensitive production sink callsite" fingerprint (`path:count:hash`). Adding a sink bumps the count/hash → snapshot mismatch → the "Data Classification Ratchet" staging-PR check fails. Fix = re-ratchet: `pnpm -F @ampersand/db exec vitest run -u src/security/__tests__/data-classification-register.test.ts`, then REVIEW the `.snap` diff is ONLY your expected new sink (it's a security gate) and commit it. Same pattern as the raw-signals sink re-ratchet.

6. **The destructive-plan guard blocks the WHOLE push-triggered staging TF apply when ANY resource needs replacement** — even a pure env-var/tfvars change won't land if an unrelated `google_compute_instance_template` replacement is pending in the plan (e.g. a fleet-host image digest moved). `guard-terraform-plan` fails the apply, and a failed TF apply SKIPS the api/mcp/web deploys (see [[feedback_prod_deploy_tf_gates_images]]) — so merges appear "done" but nothing deployed. Clear it with a MANUAL dispatch: `gh workflow run staging-deploy-orchestrator.yml --ref staging -f force_terraform=true -f terraform_destroy_intent=APPLY_DESTRUCTIVE_STAGING_PLAN -f force_api=true` (review the destructive plan first). The full orchestrator apply DOES promote Cloud Run traffic (Promote API/MCP steps), unlike a manual `gcloud run services update` (Gotcha 1 in [[reference_fleet_host_capability_provisioning]]).

7. **Poll-loop false-positive: require a minimum check count OR track the specific run.** After a push, `gh pr checks <n>` briefly shows only the fast-registering checks (e.g. just the cycle gate) with 0 pending → a naive "0 pending ⇒ done" loop reports green prematurely. Guard on `pending==0 AND total>=<expected>`, or poll the specific run via `gh run list --json name,status,headSha --jq 'select(.name=="Staging PR Validation" and .headSha==<HEAD>)'` until `completed`.

8. **Environment-scoped GitHub Actions secrets only resolve when the job declares `environment: staging`.** `ADMIN_AUTH_SECRET` (and peers) resolve to an **empty string** in any job lacking that declaration, failing silently at runtime rather than at config parse — e.g. the orchestrator's `smoke-test-admin` (no `environment:`) hit the login redirect and failed, while PR-validation's `smoke-test-admin` passed *because* it declared `environment: staging`. Sibling deploy/E2E jobs that pass all declare it; copy `environment: staging` onto the failing job. (Confirmed 2026-07-30.)

**Why:** each of these silently wasted a merge round-trip (or, for #6, made a "merged" change silently not deploy).
**How to apply:** lower-case commit subjects; keep the current-cycle ENG-XXXX the FIRST/only ref in the body + push (don't `gh run rerun`) to re-trigger the gate; register new routes in route-owns-auth; re-ratchet the data-classification snapshot for new sinks; use the poll-loop with a min-count/run-tracking guard; for a blocked destructive plan, dispatch the orchestrator manually.
