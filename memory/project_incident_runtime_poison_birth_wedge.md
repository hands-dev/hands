**2026-07-27: prod &michael's agent "not responding" — root cause was a poison-message wedge, NOT a down VM.** Recovered by operator reprovision.

**Mechanism (confirmed via serial console):** a `ampersand-get-to-know-me` **birth** (`platform_trigger`, new `lr_` attempt-boundary loop-run path) claimed the single-threaded `ampersand-runtime-channel-worker` at 20:45, hung ~37 min, lease expired (`loop_runs.error={"code":"runtime_lease_expired"}`). The worker then got stuck permanently trying to POST that terminal birth's response (`rcm_Kzm3…`): API returns **HTTP 400** because the older runtime image's failure/birth response body no longer satisfies the current `runtimeResponseSchema` (`apps/api/src/routes/runtimes.ts` — the /messages/:id/response route 400s ONLY on `invalid_request`; terminal/lease conflicts are 409). The worker treats the non-retryable 400 as a retryable temp-failure (`exit 75/TEMPFAIL`, backoff ~300s) and loops forever → never claims the real queued andee turns → app shows "not responding". Heartbeat is a SEPARATE systemd unit so `last_heartbeat_at` stays fresh (looks alive); the tell is `last_channel_poll_at` frozen + `status=degraded` + `last_error=runtime_attempt_controller_inactive` (set in startup-openclaw-runtime.sh.tftpl when channel-worker success-epoch is stale >90s). NO `runtime_health_events` row, NO alert (~4h).

**Diagnosis recipe (prod, read-only):** prod DB via [[project_raw_signal_zero_prod_throughput]] cloud-sql-proxy recipe (secret `database-url-production`, use a NON-5433 port e.g. 5434 since staging proxy squats 5433). Key tables: `agent_runtimes` (status/last_error/last_heartbeat_at vs **last_channel_poll_at**/supervisor_ready_at), `runtime_channel_messages` (queued vs error; `role='user'` even for `turn_kind='platform_trigger'` births), `loop_runs`, `runtime_pool_slots`. GCP: `gcloud compute instances list --filter=labels.billing_class=hosted-runtime` (labels carry `tenant_tag`,`runtime_id`; a claimed pool VM keeps its `runtime_pool_slot` label — cosmetic, not a double-binding). **Serial console w/o SSH: `gcloud compute instances get-serial-port-output <vm> --zone us-central1-a` — this is what revealed the poison loop.** Prod IAP-SSH is OFF (no `openclaw-rt-production-iap-ssh` firewall rule; `allow_iap_ssh=false`), so surgical on-VM fixes need a standing firewall change — avoid.

**What does NOT fix it:** cancelling a *queued* birth via `requestRuntimeChannelMessageCancellation` (only clears queued/claimed, not the already-`error` poison msg). VM reboot (`gcloud compute instances reset`) — the pending response is persisted on disk; worker resumes and re-hits the same 400.

**RECOVERY THAT WORKED — operator reprovision scoped to ONE runtime:**
`POST https://api.and.com/v1/runtimes/cohort/reprovision` header `authToken: <secret runtime-reprovision-operator-token>` (64-char, prod Secret Manager, michael can read; DISTINCT from api-auth-token — highest-privilege fleet-teardown primitive) body `{"runtimeIds":["rt_…"],"reason":"…","idempotencyKey":"<uuid, NOT retry-safe — run once>"}`. Revokes old runtime + mints fresh one on a warm-pool slot; came **online in ~45s** and a control-plane `probe` msg was `responded` (proof of function). Queued turns on the old runtime are dropped — andee re-sends. (Andee-scoped `POST /:runtimeId/reset` = `resetHostedRuntimeBootstrap` is the intended per-andee lane but needs the andee's prod device JWT AND drives GCP provisioning, so it is NOT safely runnable off-host like a pure-DB query.)

**Systemic bugs to fix (tickets pending):** (1) worker retries non-retryable HTTP 400 forever = head-of-line poison message that survives reboot and wedges the whole runtime; (2) API↔runtime response-schema skew on failure/birth responses (ENG-1374 version-skew family — all 3 named prod tenants + pool on `ocr-2026.6.5`); (3) GTKM birth hung 37min on `lr_` attempt-boundary path + re-birthed an already-onboarded andee; (4) no alert on degraded/attempt_controller_inactive w/ frozen channel-poll while heartbeats continue.
