Everything below is the RETIRED attach-on-open history — kept for the fence architecture context, but attach-on-open itself is gone.

**Goal (ENG-1384):** clicking & opens the chat INSTANTLY, andee types immediately, a fleet chat host attaches in the BACKGROUND, and the only feedback is a soft "connecting to agent → agent connected" — never a blocking "Preparing agent" screen. Builds on the ENG-1383 chat cutover (see [[project_eng1383_chat_cutover]], [[reference_fleet_host_capability_provisioning]]). Branch `feature/eng-1384-assign-on-open`. All gated behind the per-andee canary `FLEET_CHAT_ANDEE_ALLOWLIST` + `FLEET_CHAT_ATTACH_ON_OPEN` (both OFF by default) — nothing is live.

**The load-bearing discovery — a fleet checkout fences the andee's runtime to `status='provisioning'` for the ENTIRE serve and nothing flips it back to `online`.** So BOTH conversation fences gated on `online` had to be relaxed SYMMETRICALLY, or chat over fleet hosts simply never delivers:
- **L3 send fence** (`createRuntimeChannelMessage`, `packages/db/src/queries/agent-runtimes.ts`): admits an andee turn while provisioning when a host serves THIS conversation.
- **L4 claim fence** (`claimRuntimeChannelMessage`, same file ~5079-5171): the fleet host consumes messages ONLY via `claimRuntimeChannelMessage` (the `POST /:runtimeId/messages/claim` runtime-poll, as the runtime) — there is NO checkout-specific drain. It gated `user` rows on `isRuntimeReadyForChannel` (online/degraded only) → for a provisioning fleet runtime it handed out only `probe` rows and returned `runtime_not_ready`, which the host runner (`checkout_executor.py held_chat_session`) treats as FATAL on its first claim → the queued turn strands. Fix: `serviceable = channelReady || servingChatCheckoutSessionId(...)`, hand out that checkout's conversation `user` rows, long-poll (not fatal) when nothing queued. **L3 without L4 is useless** — that was the trap.
- **L1b connection-state** (`getFleetChatConnectionStateForConversation`): read-only `connecting|connected` hint on `GET /:runtimeId/messages` (canary-gated). `connected` == the exact same predicate, so the UI can't claim connected while a send/claim would fence.

**One shared predicate for all three:** `servingChatCheckoutSessionId(executor, {runtimeStatus, checkoutTaskId, andeeId})` returns the session id the runtime's LIVE checkout serves, or null. "Live" mirrors `authorizeHostedRuntimeMcpSession`'s proof (~agent-runtimes.ts:2791-2803): provisioning + checkout bound to a `chat_bridge` task for this owner, `claimed`/`running`, with an UNEXPIRED lease (`gt(leaseExpiresAt, clock_timestamp())`). The lease check is load-bearing — a crashed host's task row stays `running` with an expired lease for a window before reaping; without it a dead host reads as serving. NOTE the auth layer (`authenticatedRuntimePredicate` → `checkoutBoundRuntimeLiveLeasePredicate`, `agent-runtime-auth.ts`) ALREADY enforces checkout-lease-liveness, so a dead-host claim gets `unauthorized` before the L4 fence even runs (defense in depth).

**L2 open-attach — mobile has NO open-time POST and its send path BYPASSES L1.** `resolveLegacyRuntimeThreadConversation` (the mobile GET/POST `/:runtimeId/messages` shim path, `apps/api/src/services/conversations.ts:1017`) mints via `mintConversationForContract` DIRECTLY, skipping `resolveConversationForAndee` where the L1 attach-on-open hook lives (:637). So attach-on-open was unreachable from mobile, and the L3 fence blocks the first send until a host connects → deadlock. Fix = new andee-keyed **`POST /v1/chat/open`** (`apps/api/src/routes/chat.ts` → `openAgentChatForAndee`): resolves the agent conversation via `resolveConversationForAndee({surface:{kind:'agent'}})` (mint + L1 attach) and returns `connectionState`. NOT runtime-namespaced — the client may open before it has a runtime (Michael's steer); the andee's active runtime is resolved server-side via `getActiveAgentRuntimeForAndee`.

**THE CHURN ROOT CAUSE + THE TWO FIXES (found during live staging testing):** every fleet chat host quarantined (`executor:chat_claim_rejected`) after ~one turn, then got reaped + replaced (new host id → stale cohort → no chat → manual re-point). Two independent causes, two fixes:
- **Runner fatal-on-409 (PR #2318, `held_chat_session` in `checkout_executor.py`):** a 401/409 from `channel.claim()` is often TRANSIENT (a brief checkout lease-renewal gap, or the reconciler moving the checkout between hosts), but the runner `fail()`ed → host quarantine on the FIRST one. Fixed: retry 401/409 bounded (`CHAT_CLAIM_NOT_OURS_MAX_ATTEMPTS=6` × `5s`, under the 60s local lease watchdog) with backoff; 404 stays fatal. NOTE the checkout-lease renewal ALREADY runs on a separate `threading.Thread` (`_start_lease_renewal`, 15s cadence) — a long LLM turn does NOT lose the lease; that was NOT the bug.
- **Host-id cohort staleness (PR #2319, `FLEET_CHECKOUT_CONSUMER_ALL`):** see [[reference_fleet_host_capability_provisioning]] Gotcha 3 — retire the host-id consumer cohort on staging so recycled hosts auto-advertise chat with no re-point. Isolation was always at the matchmaker's per-andee allowlist.
