**Decision (2026-07-28):** retire `runtime_channel_messages`, make `tasks` the single work queue for all agent execution (background + user-directed). Managing both (today's additive `chat_bridge` dual-write) is a liability: two fences, two terminalization seams, silent divergence, split-brain dispatch.

**Key insight — decompose, don't relocate.** `runtime_channel_messages` fuses two concerns: (1) work dispatch → moves to `tasks`; (2) the client-facing conversation log (history + streamed preview + terminal read the app polls via `GET /messages`) → moves to a dedicated **read store**, fed by task terminalization. `tasks` today carries NO content/preview/result (`schema/tasks.ts:63-65` = `directive_ref` pointer + `terminal_code` only); it must gain a directive payload + preview/checkpoint surface + result payload.

**Two architectures today (see bridge doc).** Dedicated per-andee runtime (`agent_runtimes` + `runtime_channel_messages`, live path) vs. fungible fleet (`tasks` INN-187 + `fleet_hosts` INN-193, staging-flag-gated). Bridged by INN-210 checkout fence (`agent_runtimes.checkout_task_id/host_id/epoch`) + INN-190 `chat_bridge` dual-write (`conversations.ts:89-101`).

**Task registry (`packages/db/src/queries/task-registry.ts`):** types = chat_bridge, fleet_upgrade, location_enrichment, photo_enrichment, **loop_advance** (cadence loop turn, SLA 30, cap `loops`, keyed `${loopId}:${nextRunAt}`), workspace_acceptance. GOTCHA: `loop_advance` is a SIMULATION — producer exists (`loop-cadence-scanner.ts`, INN-192) but nothing claims it; fleet executor only maps `chat_bridge→chat` (`checkout_executor.py:165-172`). GAP: user-directed loop turns have no loop task type — they masquerade as generic `chat_bridge` (loses loopId + `loops` cap). Fix = new `loop_chat` hybrid type (INN-221).

Refill by PROVISION when under VM cap, EVICT when cap-bound. Detach never on the waiting andee's critical path (pool pre-cleaned).
