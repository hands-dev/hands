**How a fleet host advertises a capability (the gate chain).** A host reports `fleet_hosts.capabilities = ["<cap>"]` only when `checkout_executor.py`'s `capabilities()` passes ALL of: (1) `consumer_gate_ready()` — the host's `/run/ampersand-fleet-host/checkout-consumer-enabled` marker == `1`, set from the heartbeat RESPONSE only when the host id is in the API's `FLEET_CHECKOUT_CONSUMER_HOST_IDS`; (2) `ready(require_runtime_delegation=True)` — gateway/watcher/runner/installation/delegation/cgroup all ready (a persistent identity-neutral OpenClaw gateway runs on `127.0.0.1:18790` even on idle hosts); (3) the per-capability gate. For `chat`: `chat_adapter_ready()` (root-owned `chat-config.json` + executor as adapter) AND `chat_model_access_ready()` (runs `openclaw models status --check --probe`). Server only stores measured caps for a host on the measured-v1 + `FLEET_CHECKOUT_CONSUMER_HOST_IDS` allowlist. `capabilities()` swallows exceptions → returns `[]`, so failures are SILENT (host just reports `[]` forever). Debug on-host: `gcloud compute ssh <instance> --tunnel-through-iap`, then run `/opt/ampersand-fleet-host/checkout-executor.py … capabilities` as root; check the marker + run the probe manually sourcing `/etc/ampersand-fleet-host/engine.env`.

**GOTCHA 1 — env-only staging applies DON'T promote Cloud Run traffic (bit us 4×).** The staging deploy's "Sync env-only Cloud Run traffic" step creates a NEW `api-server` revision carrying the changed env (`FLEET_HOST_DESIRED_IMAGE_VERSION`, `FLEET_CHECKOUT_CONSUMER_HOST_IDS`, `FLEET_CHAT_ANDEE_ALLOWLIST`) but leaves 100% traffic pinned to the OLD revision. So the fleet keeps seeing STALE desired-image/cohort and nothing changes. After EVERY env-changing apply, verify `gcloud run services describe api-server --format=json` traffic[0] and `gcloud run services update-traffic api-server --to-revisions=<new-rev>=100`. Same trap when editing env directly via `gcloud run services update` (traffic stays pinned). NOTE: `--update-env-vars` with a comma-containing value needs the `^;^` custom-delimiter form.

**GOTCHA 2 — an executor/template change forces a DESTRUCTIVE recycle.** `fleet_host_image_version = flh-<openclaw>-b<sha256(fleet_executable_bootstrap_contract_digest)[:12]>` (`staging/main.tf:142`). Any change to `checkout_executor.py` / `workspace_runner.py` / startup template bumps that digest → the `google_compute_instance_template.fungible_host` must be REPLACED → `guard-terraform-plan.mjs` blocks push-triggered staging deploys ("cannot apply destroys"). You MUST manually dispatch: `gh workflow run staging-deploy-orchestrator.yml --ref staging -f force_terraform=true -f terraform_destroy_intent=APPLY_DESTRUCTIVE_STAGING_PLAN` (add `-f force_api=true` if the API image also needs deploying). Recycle is then driven by the internal drain cron (`reconcileFleetHostPool`, `apps/api/src/routes/internal.ts:210`, ~5 min): it drains `ready` hosts whose `image_version != FLEET_HOST_DESIRED_IMAGE_VERSION` (the SERVING API's value — so Gotcha 1 blocks the recycle if traffic isn't promoted) and provisions fresh ones from the new template.

**GOTCHA 3 — host-id churn makes `FLEET_CHECKOUT_CONSUMER_HOST_IDS` fragile. RETIRED on staging by ENG-1384 (`FLEET_CHECKOUT_CONSUMER_ALL`).** Every recycle/reap mints NEW `fleethost_` ids; a host-id cohort goes stale on every churn and the new hosts advertise `[]`, forcing a manual re-point. **Fix (2026-07-29, PR #2319):** `FLEET_CHECKOUT_CONSUMER_ALL=true` makes EVERY authenticated host a consumer — no id list, so a recycled host auto-advertises its caps with zero re-point. `isFleetCheckoutConsumerHostEnabled()` returns true when the flag is set. Isolation of WHOSE work runs on fleet hosts was ALWAYS at the orchestration layer (the matchmaker's per-andee `FLEET_CHAT_ANDEE_ALLOWLIST` / `chatCutoverBlocksAssignment`, `task-matchmaker.ts`), keyed on the stable andee id — NOT the host cohort. So retiring the cohort changes nothing about blast radius. It's SERVER-ONLY (runner reads `checkoutConsumerEnabled` from the heartbeat response, `fleet.ts:1385`) → deploys via a normal api env change, no recycle. Staging: `fleet_checkout_consumer_all=true`, host-id list emptied. **Production still uses the explicit host-id cohort** for a cautious rollout, so the old chase still applies there until prod also flips to consumer-all. The three "dances": (1) cohort re-point → dead via consumer-all; (2) hosts quarantining/churning per chat turn → dead via the runner retry-on-409 (PR #2318); (3) the destructive `APPLY_DESTRUCTIVE_STAGING_PLAN` dispatch → STAYS, but only for fleet-host IMAGE changes (Gotcha 2) — api-only / flag-only changes ship on a normal merge.

**GOTCHA 4 — capability key ≠ task-type name, hand-mirrored in two languages.** Source of truth = `packages/db/src/queries/task-registry.ts` `TASK_REQUIRED_CAPABILITY` (`chat_bridge→chat`, `loop_advance→loops`, `location_enrichment→location`, `photo_enrichment→photo`, `workspace_acceptance→workspace-acceptance`). The fleet host RE-DECLARES this by hand in `checkout_executor.py` `TASK_TYPE_CAPABILITY` (+ a jq allowlist in `startup-fleet-host.sh.tftpl`, + the tenant runtime template). Drift = silent break. Capabilities are a deliberately COARSER grouping (`loops` serves both `loop_advance` and `loop_chat`), so don't blanket-rename to 1:1 — add a drift-guard test instead. (Guard is a pending ENG-1383 follow-up.)

**GOTCHA 5 — a stale queued task poison-loops the moment a capable host appears.** A days-old queued `chat_bridge` (stale `session_id`) gets assigned → a fleet host claims it → checks out + FENCES the andee's `agent_runtimes` row → `execute_chat_bridge` fails (no live conversation) → requeues → the other host re-claims → loops, holding the andee runtime in `provisioning`/offline and keeping the hosts busy (so they drop the capability while busy). Flush stale tasks BEFORE enabling. Manual flush (staging): `UPDATE agent_runtimes SET checkout_task_id=NULL, checkout_host_id=NULL, checkout_epoch=NULL, checkout_bound_at=NULL, checkout_runtime_auth_issued_at=NULL WHERE checkout_task_id IS NOT NULL;` (ALL five fence cols — the `agent_runtimes_checkout_fence_shape` check is all-or-nothing) then `UPDATE agent_tasks SET status='cancelled', terminal_at=now(), terminal_code='manual_flush', claim_token_hash=NULL, lease_expires_at=NULL, last_heartbeat_at=NULL WHERE status IN ('queued','claimed','running');`.

**Chat-specific readiness bugs found + fixed (ENG-1383).** `chat_model_access_ready` in `checkout_executor.py` had two latent bugs that meant chat NEVER worked on the fleet: (a) `--probe-max-tokens 1` — OpenAI's Responses API rejects `<16` (HTTP 400) for `gpt-5.5` → fixed to `CHAT_MODEL_PREFLIGHT_MAX_TOKENS = 16`; (b) subprocess wall-clock timeout = `CHAT_MODEL_PREFLIGHT_TIMEOUT_MS/1000+2 = 5s` but the `openclaw models status --probe` CLI takes ~17s (startup + ~3.5s model call) → decoupled into `CHAT_MODEL_PREFLIGHT_SUBPROCESS_TIMEOUT_S = 30` (leave `--probe-timeout` = the 3s model budget). The ~13s CLI startup is inflated by a BLOCKED codex plugin: `useradd --system and-fleet-runtime` gets uid 999, `openclaw onboard` runs as that user so `$ENGINE_ROOT/.openclaw/@openclaw/codex` is owned by 999, but the root-run probe (`env HOME=engine root`) trips OpenClaw's "suspicious ownership (uid=999, expected root)" guard → re-scans every probe. It does NOT fail the openai auth probe (noise/cost, not a blocker); the 1:1 tenant runtime (`startup-openclaw-runtime.sh.tftpl:4726`) has the same `--probe-max-tokens 1` bug, unfixed.

**GOTCHA 6 — a `failed` fleet_hosts row is an orphan tombstone the reconciler NEVER cleans up.** When a backing-VM create hits a deterministic pre-accept failure, `failFleetHost` sets `status='failed'` (comment says "so the next reconcile can replace it without consuming maxTotal headroom"). But `failed` appears in NONE of `reserveFleetHostsForReconcile`'s predicates — not `ready`, not `active` (booting-fresh/busy/flushing/cleaning/assigned/ready), not the stale/drain set (booting-stale/stale-ready/quarantined/draining). So it's correctly NOT counted against capacity, but it's also never swept: the pool silently replaces it (fresh hosts reach target) while the dead row lingers indefinitely as a `failed` tombstone with its VM already gone. Remediation for a "failed staging fleet host" that's really just this orphan: confirm the VM is gone (`gcloud compute instances describe <gcp_instance_name>` → not found), then delete the row — same op the reconciler's drain runs (`deleteFleetHost`). Guarded manual delete: `DELETE FROM fleet_hosts WHERE id='<id>' AND status='failed' AND last_heartbeat_at IS NULL AND image_version IS NULL;`. Verified 2026-07-29: pool was at target=2 with two fresh chat hosts; the lingering row was a 07-28 tombstone. (Separately observed: chat hosts flap `ready ["chat"]`↔`booting []` when the flaky chat probe transiently measures `[]` — a heartbeat with empty caps demotes ready→booting per the upsert `measuredUnhealthy` branch; recovers on next passing probe. See the ENG-1383 probe-flakiness notes above.)
