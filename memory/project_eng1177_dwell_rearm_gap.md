**ENG-1177 (filed 2026-07-03, High, cycle 22, assigned Michael).** The mobile CLVisit dwell rail (`location_ping` → server dwell → `place_affinities`/venue suggestions) silently dies for consented andees with **no in-app recovery path** — suppresses the whole dwell product fleet-wide.

**Root cause (verified on origin/main):** CLVisit is armed only by `startVisitMonitoring()`, reached ONLY inside a successful `requestLocationTier('always')` — 3 call sites: onboarding `components/LocationConsentBody.tsx:70`, `app/(loop-creation)/get-to-know-me.tsx:207`, `app/location-settings.tsx:116`. There is **no boot/session-restore re-arm** (grep of auth-context/_layout/index = none), and once consented `location-settings.tsx` gates its CTA `onPress={isUndetermined ? onAllow : onOpenSettings}` so a granted andee only gets "Manage in iOS Settings" (`Linking.openSettings()`) — which does NOT arm CLVisit. Granting Always via iOS Settings also never arms it. So arming happens once, transiently, at first grant; any relaunch / TestFlight build update leaves it dark forever.

**Evidence:** prod &michael (`4DHFDJ8Uccv8nmGr8nG7Yj9nm9zS`) had 0 `location_ping` all-time despite Location=Always + Background App Refresh on; all his venues are `origin='photo_scan'`. Fleet: only 24 `dwell`-origin `place_affinities` vs 316 `photo_scan` (most consented users are in the dark state). See [[project_raw_signal_zero_prod_throughput]] for the prod-DB diagnostic recipe.

**Fix (BUILT + typechecks, NOT committed — worktree-1 on branch `fix/eng-1093-skip-continue-stall`, 12 behind origin/main; auth-context/location.ts identical across HEAD/main/staging so it applies anywhere).** `rearmVisitMonitoringIfGranted({force})` in `apps/mobile/lib/location.ts`, called from `AuthProvider` (`apps/mobile/lib/auth-context.tsx`). REVISED after a high-effort `/code-review` that found the first cut (plain `startVisitMonitoring`) was a NO-OP for the target population:
- **`force:true` on login/restore = STOP→START, not start.** The Visits TaskManager task persists across relaunch (consumer has no `taskConsumerVersion`) but its native CLLocationManager doesn't; a plain start dedups to `setOptions` no-op in EXTaskService and never rebuilds the manager. Only unregister(`didUnregister`)→register(`didRegisterTask`) news up a fresh manager. Keyed on `andeeId`.
- **Foreground (`AppState 'active'`, `force:false`)** = cheap start-if-not-monitoring → catches a mid-session upgrade to Always in iOS Settings.
- **Logout teardown**: `stopVisitMonitoring()` in `logout()` — else the prior andee's visit task records `location_ping` under the NEXT andee's session (cross-andee attribution bug the review caught).
- **Observability**: Sentry breadcrumbs on re-arm outcome + `captureWithTags` on failure.
